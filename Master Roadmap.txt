Stage 4.5g — Tactical Foundation Lock

Status: Next
Purpose: Verify and freeze the existing tactical foundation before building substantial content.

Stage 4.5f corrected the movement–Reaction architecture, but its runtime test suite has not yet been run in an environment containing Godot. Stage 4.5g converts the current working archive into a trusted baseline.

4.5g1 — Complete runtime validation

Run every existing Godot test suite, not only the Stage 4.5f runner.

Validation must cover:

campaign transactions;
character resolution;
inventory;
mission setup and result handling;
tactical movement;
stealth and detection;
initiative;
combat;
bodies and captives;
extraction;
cover;
visibility;
Reactions;
interrupted movement.

Repair:

parser errors;
stale constructor calls;
invalid preloads;
missing resources;
runtime type failures;
tests that only pass because they inspect source strings rather than behaviour.
4.5g2 — Explicit invalidation contracts

Stage 4.5f improved reason coverage and added a safe full-refresh fallback. The next step is to stop using reason strings as the authoritative source of invalidation.

Every production TacticalChangeSet must carry an explicit contract:

var changes := TacticalChangeSet.new(
	&"inventory_transfer",
	state.revision
)

changes.set_invalidation_contract(
	TacticalInvalidationContract.inventory_changed(
		affected_character_ids
	)
)

The contract should be able to identify:

token status
action budget
inventory
occupancy
specific moved observers
team visibility
geometry
initiative
environment
combat log
mission state

The reason remains useful for diagnostics but does not decide what refreshes.

Required behaviour
An ordinary attack does not rebuild visibility.
Moving one observer does not recalculate every observer.
Inventory transfer does not rebuild board geometry.
A life-state change updates tokens, initiative and occupancy only where required.
Opening a Reaction prompt does not refresh fog.
Unknown or missing contracts fail validation.
4.5g3 — Immutable mission identity

Finish the existing mission boundary before more mission content depends on it:

MissionSetupSnapshot.finalise()
→ canonical setup payload
→ immutable setup hash
→ tactical mission
→ MissionResult.source_setup_hash
→ campaign commit verifies the hash

The canonical hash should include gameplay-relevant data:

mission instance ID;
mission definition ID;
region and site;
map identity or map seed;
objective definitions;
deployed character IDs;
deployed item IDs and starting locations;
difficulty and rules profile;
authorised mission metadata.

It must not depend on:

dictionary ordering;
object memory addresses;
presentation state;
editor-only metadata;
non-gameplay timestamps.

After finalisation, all mutation methods must reject changes to mission identity, deployment, objectives or metadata.

4.5g4 — Trusted generated-item provenance

Introduce authority for items that come into existence during tactical play.

GeneratedItemProvenanceRecord
├── provenance ID
├── mission ID
├── source setup hash
├── generated item ID
├── creation kind
├── source entity or structure
├── creation event ID
├── tactical revision
├── item definition
├── quantity
└── consumed/committed state

Initial creation kinds should support:

structural salvage;
transformed equipment;
mission-crafted items;
corpse-generated loot;
magically created persistent items.

MissionResult may reference a provenance record. It may not create the record that proves its own legitimacy.

Stage 5.5 — Notoriety and Base Defence

Purpose: Complete the campaign pressure loop.

Killed settlement guards: +8
Killed civilians: +12
Destroyed granary: +10
Stole supplies unnoticed: +3
Released captives: -2
Total: +31

Repeated events are grouped, but every point remains explainable.

Threshold behaviour

Suggested presentation:

0–49   Local concern
50–74  Organised investigation
75–99  Retaliation preparing
100    Raid operation created

The exact labels can be tuned without introducing a second hidden threat meter.

Raid operation

At 100:

create one incoming raid;
identify its origin;
show force composition;
show arrival time;
show approach route;
allow preparation;
permit interception only when explicitly authored.

Resolving the raid reduces that region’s Notoriety by 50, following the current stronghold design.

Base-defence assembly

The player’s actual facility layout must generate the defence map:

stronghold grid
→ facility modules
→ automatic connectors
→ entrance and Heart
→ tactical defence map

The first implementation needs only the currently supported facilities and authored connection rules.

Stage 5.5 completion gate
